# Bigger Context：传输修复与实际限制

2026-09-14，`5.0.6-bridge.8`。

## 原故障与修复

本机 launcher.jsonl 中 `6799068b5596_fallback`（2026-09-13 11:03–11:04，北京时间）
两次传输都是三段、约 85,535 输入 Token。前两段使用 Low，每段约 30,460 Token。
第一段 ACK 成功，第二段发送被接受后，ACK 等待分别在 129ms、93ms 失败。
只有通用网页错误，**没有后端明确的 context_length_exceeded 证据**。

`resolveChatGptWebMultipartStagingMode` 原先只依据最大单段长度选最便宜的模式。
这忽略了后续 ACK 请求仍携带前段历史。修复让实际执行路径优先使用用户请求的模式，
不再将 High/Medium 的分段降为 Instant/Low；若单段传输限制要求，则只能提升到支持的模式。
最后一段仍使用用户原来选择的模式。保留现有字符、单消息 Token、图像预算检查。

新增每段 `messageTokens`、`cumulativeVisibleTokens` 和实际 `effort` 日志。
累计值包含此前确认的 ACK，不包括不可见平台上下文；不记录输入正文或凭据。

本次不是改 task ID、复用最终答案或压缩计数。上述第二段故障不能解释为 ID 错配；
也不能凭此排除其他请求可能出现不同问题。

## 使用结论

分成多条消息能绕开部分**单条输入传输限制**，但不会增加底层模型的物理上下文容量。
向 Codex 声明 3× 阈值也是客户端配置，不能保证网页真正保留三倍内容。
因此修好了错误降档的传输路径，**不代表已验证可靠的 270k 上下文**。
默认保持关闭；重要工作不建议依赖三倍模式。没有自动修改用户的开关或原有 Provider、网络设置。
UI 增加“较早分段可能丢失”的明确警告。

定向 staging/preflight 回归 4 项通过，TypeScript 类型检查通过。
额外运行的混合密度大样本旧测试触发其 20 秒性能超时，不算通过；
其余该次运行的 5 项通过。真实传输测试使用当前源代码，不修改正在运行的 Codex 配置。
